# Developer Getting Started

OpenTelemetry can be used by developers who want to add observability to their applications, whether they are instrumenting application code directly or using instrumentation that is already available for their language, framework, or library.

A typical developer workflow looks like this:

**Choose your language → choose an instrumentation approach → instrument your application → generate telemetry → export telemetry → verify the result → add custom instrumentation**

## 1. Choose your programming language

OpenTelemetry provides APIs, SDKs, and instrumentation support for a wide range of languages.

Choose the language used by your application:

* [C++](../languages/cpp/)
* [.NET](../languages/dotnet/)
* [Erlang/Elixir](../languages/erlang/)
* [Go](../languages/go/)
* [Java](../languages/java/)
* [JavaScript and TypeScript](../languages/js/)
* [PHP](../languages/php/)
* [Python](../languages/python/)
* [Ruby](../languages/ruby/)
* [Rust](../languages/rust/)
* [Swift](../languages/swift/)
* [Other languages](../languages/other/)

Each language has its own APIs, SDKs, instrumentation libraries, and setup instructions.

If your application uses a language or framework with existing OpenTelemetry instrumentation, you can often start collecting telemetry without writing instrumentation yourself.

## 2. Choose an instrumentation approach

There are two primary ways to instrument an application.

### Automatic or zero-code instrumentation

Automatic instrumentation lets you generate telemetry without modifying your application code.

It can be useful when:

* You want to instrument an existing application quickly.
* You want to minimize code changes.
* Your language and framework are supported by available instrumentation.
* You want to establish baseline observability before adding custom instrumentation.

See [Zero-code Instrumentation](../zero-code/) for available options.

### Code-based instrumentation

Code-based instrumentation gives you direct control over the telemetry generated by your application.

Use it when you need to:

* Instrument application-specific operations.
* Add meaningful spans or metrics around business logic.
* Add attributes that provide application-specific context.
* Create custom instrumentation where automatic instrumentation does not provide enough information.

See [Code-based Instrumentation](../concepts/instrumentation/code-based/) for more information.

### You can use both

Automatic and code-based instrumentation are not mutually exclusive.

A common approach is to start with automatic instrumentation to establish basic visibility and then add custom instrumentation where additional application context is valuable.

## 3. Understand the telemetry signals

OpenTelemetry supports several types of telemetry, known as signals.

### Traces

Traces describe the path of a request through an application or distributed system.

They help you understand:

* Where a request spent time.
* Which services were involved.
* Where failures occurred.
* How services depend on one another.

### Metrics

Metrics are measurements collected over time.

They can help you monitor:

* Request rates.
* Error rates.
* Latency.
* Resource utilization.
* Application and service performance.

### Logs

Logs record events generated by applications and infrastructure.

OpenTelemetry can collect and correlate logs with other telemetry so that you can investigate an event in the context of the corresponding traces and metrics.

### Profiles

Profiles provide information about how applications consume resources such as CPU and memory.

See [Signals](../concepts/signals/) to learn more about the telemetry signals supported by OpenTelemetry.

## 4. Generate and export telemetry

After instrumentation is configured, your application can generate telemetry. You then need to decide where that telemetry should go.

There are two common approaches:

* Export telemetry directly from the application to an observability backend.
* Export telemetry to an [OpenTelemetry Collector](../collector/), which then sends it to one or more backends.

Direct export can be a simple way to get started.

A Collector is particularly useful when you need a central place to receive, process, route, or export telemetry.

## 5. Verify your telemetry

After configuring instrumentation and export, verify that telemetry is actually being generated and received.

Check that:

* The application is generating the expected telemetry.
* The configured exporter is running correctly.
* The destination is reachable.
* The observability backend is receiving the telemetry.
* Traces, metrics, or logs contain the information you expect.

Start with a simple application and a small amount of telemetry. Once the basic pipeline works, expand your instrumentation and configuration.

## 6. Add application-specific instrumentation

Automatic instrumentation can provide valuable baseline information, but it may not know what is important to your application.

Add custom instrumentation when you need visibility into application-specific operations.

For example, you might instrument:

* A business transaction.
* A database operation.
* A queue-processing operation.
* An external service call.
* A significant application workflow.

Use attributes and other telemetry context to make the resulting telemetry useful when investigating problems.

See [Instrumentation](../concepts/instrumentation/) and [Semantic Conventions](../concepts/semantic-conventions/) for guidance on adding meaningful context to telemetry.
