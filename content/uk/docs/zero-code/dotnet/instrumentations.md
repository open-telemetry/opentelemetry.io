Автоматичне інструментування OpenTelemetry .NET підтримує широкий спектр бібліотек.

## Інструментування {#instrumentations}

Усі інструментування стандартно увімкнені для всіх типів сигналів (трейси, метрики та логи).

Ви можете вимкнути всі інструментування для певного типу сигналу, встановивши змінну середовища `OTEL_DOTNET_AUTO_{SIGNAL}_INSTRUMENTATION_ENABLED` в значення `false`.

Для більш детального підходу ви можете вимкнути конкретні інструментування для даного типу сигналу, встановивши змінну середовища `OTEL_DOTNET_AUTO_{SIGNAL}_{0}_INSTRUMENTATION_ENABLED` в значення `false`, де `{SIGNAL}` — це тип сигналу, наприклад `TRACES`, а `{0}` — це чутлива до регістру назва інструментування.

\[3\]: Приймач PostgreSQL з OpenTelemetry Collector Contrib надає це значення як `postgresql.application_name` у своїй [події `db.server.query_sample`](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/42f949127580c0d00088b785cd0b35842dc0ddb8/receiver/postgresqlreceiver/metadata.yaml). Збір вибірок запитів вимкнено стандартно і вимагає `pg_monitor`; дивіться [закріплену конфігурацію приймача](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/42f949127580c0d00088b785cd0b35842dc0ddb8/receiver/postgresqlreceiver/README.md). Поширення виконує `SET application_name` через синхронний [шлях `ExecuteInternalCommand`](https://github.com/npgsql/npgsql/blob/d3768398c17877b3a916c3c4d87e8e11698991fc/src/Npgsql/Internal/NpgsqlConnector.cs#L2864-L2875) Npgsql перед кожною операцією з трасуванням. Npgsql скидає цю команду та очікує на її відповіді `CommandComplete` і `ReadyForQuery`, тому поширення додає один обмін із базою даних на кожну операцію з трасуванням. Воно не змінює, не додає префіксів і не обʼєднує SQL застосунку. Коли Npgsql завершує дію користувача, поки він усе ще володіє зʼєднувачем, інструментування виконує `RESET application_name` через той самий шлях. Це додає один обмін для очищення на кожну поширену операцію та скидає значення до стандартного для сесії, налаштованого під час відкриття зʼєднання, до того як керування повертається тому, хто викликає, або зʼєднувач можна використати для іншої операції. PostgreSQL [`RESET`](https://www.postgresql.org/docs/18/sql-reset.html) не відновлює значення, присвоєне пізніше через `SET`; тому ввімкнення цієї опції може перезаписати зміни `application_name`, зроблені кодом застосунку під час виконання. Дивіться [життєвий цикл `EndUserAction`](https://github.com/npgsql/npgsql/blob/d3768398c17877b3a916c3c4d87e8e11698991fc/src/Npgsql/Internal/NpgsqlConnector.cs#L2687-L2724) Npgsql. Ці внутрішні команди використовують потік Simple Query у PostgreSQL, який відкидає попередній безіменний оператор і портал; явно підготовлені та автоматично підготовлені оператори Npgsql є іменованими і залишаються повʼязаними з фізичним зʼєднанням. Дивіться [правила протоколу розширених запитів](https://www.postgresql.org/docs/17/protocol-flow.html#PROTOCOL-FLOW-EXT-QUERY) PostgreSQL та [документацію щодо підготовлених операторів](https://www.npgsql.org/doc/prepare.html) Npgsql. Оскільки `SET` і `RESET` є справжніми операторами PostgreSQL, спостерігач, що виконує опитування під час їх короткого виконання, теоретично може їх зафіксувати. Очищення відкладається, поки транзакція перебуває в стані помилки, щоб `ROLLBACK` міг виконатися першим, а потім виконується, коли дія відновлення успішно завершується. Операції COPY у Npgsql 10+ охоплюються через його [життєвий цикл `TraceCopyStart`](https://github.com/npgsql/npgsql/blob/d3768398c17877b3a916c3c4d87e8e11698991fc/src/Npgsql/Internal/NpgsqlConnector.cs#L2964-L2980). Мультиплексування не підтримується: `application_name` є станом фізичної сесії, тоді як Npgsql може записувати кілька логічних команд до одного зʼєднувача в одному [циклі мультиплексування](https://github.com/npgsql/npgsql/blob/d3768398c17877b3a916c3c4d87e8e11698991fc/src/Npgsql/MultiplexingDataSource.cs#L176-L199). Інструментування безпечно пропускає поширення та записує одне попередження, коли виявляє мультиплексований зʼєднувач.
