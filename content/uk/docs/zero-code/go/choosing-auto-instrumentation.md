Для застосунків Go OpenTelemetry надає два різні підходи «без програмування» до інструментування застосунків без зміни вихідного коду: **приєднання під час виконання** та **вплітання під час збірки**.

Цей посібник порівнює [OpenTelemetry eBPF Instrumentation (OBI)](/docs/zero-code/obi/) та [Go compile-time інструментування OpenTelemetry](/docs/zero-code/go/compile-time/) (`otelc`), щоб допомогти вам обрати правильний інструмент для вашого середовища.

> **Примітка:** Інформацію про Go auto-instrumentation SDK дивіться в розділі [Автоматичне інструментування](/docs/zero-code/go/autosdk/). Цей посібник присвячено саме порівнянню підходів без коду на основі eBPF та compile-time.

Це посібник із прийняття рішень, а не рейтинг. Обидва проєкти є офіційними компонентами OpenTelemetry. У багатьох конфігураціях вони розвʼязують різні задачі або навіть добре працюють разом.

## Дві моделі мислення {#the-two-mental-models}

Під час оцінювання інструментування без програмування корисно розуміти фундаментальну архітектурну різницю між цими двома підходами:

- **Під час виконання (eBPF):** Інструментування працює поряд із вашим застосунком як окремий процес (часто на хост-вузлі). Воно спостерігає за застосунком ззовні — зокрема на рівні застосунку, ядра та мережі. Хоча воно може впроваджувати вихідні заголовки в простір памʼяті застосунку для поширення контексту трасування, воно не вимагає змін у процесі збірки застосунку.

- **Під час компіляції (otelc):** Інструментування впроваджується у вихідний код застосунку під час компіляції. Отриманий бінарний файл містить логіку телеметрії нативно, тобто зовнішній агент під час виконання не потрібен.

## OBI {#obi}

[OpenTelemetry eBPF Instrumentation (OBI)](/docs/zero-code/obi/) використовує eBPF ([Що таке eBPF?](https://ebpf.io/what-is-ebpf)) для автоматичної перевірки виконуваних файлів застосунків та мережевого рівня ОС.

- **Як воно підключається:** Розгортає eBPF-проби в ядрі Linux та застосунку, щоб захоплювати відрізки трейсів і метрики під час системних викликів та передавання мережевих пакетів.
- **Підтримка мов:** Широка і по суті поліглотна. Підтримує Java, .NET, Go, Python, Ruby, Node.js, C, C++ та Rust, серед інших.
- **Експлуатаційні вимоги:** Потребує середовища Linux (ядро 5.8+ або певні зворотні перенесення), підтримки BTF та підвищених привілеїв (root або певні можливості Linux).
- **Створювана телеметрія:** Найкраще підходить для захоплення трейсів (вхідних і вихідних відрізків для HTTP/S, gRPC, запитів до баз даних), метрик RED (Rate, Errors, Duration), мережевих потоків та збагачення логів. Воно захоплює те, що входить і виходить із процесу, але внутрішні відрізки, специфічні для фреймворків або бібліотек застосунку, все ще потрібно вказувати вручну, або змінюючи код застосунку, або вручну визначаючи ділянки коду у файлі конфігурації.

## otelc {#otelc}

[Go compile-time інструментування OpenTelemetry](/docs/zero-code/go/compile-time/) (`otelc`) використовує механізм `-toolexec` інструментарію Go, щоб автоматично впроваджувати інструментування OpenTelemetry безпосередньо у бінарний файл вашого застосунку під час компіляції.

- **Як воно підключається:** Перехоплює компіляцію пакетів, зіставляє функції з правилами інструментування та впроваджує гачки OpenTelemetry безпосередньо у скомпільований бінарний файл.
- **Підтримка мов:** Лише Go.
- **Експлуатаційні вимоги:** Потребує доступу до конвеєра збірки Go. Оскільки інструментування вбудоване в бінарний файл, воно працює всюди, де працює бінарний файл Go, і не потребує спеціальних привілеїв ОС або функцій ядра під час виконання.
- **Створювана телеметрія:** Забезпечує глибокі відрізки всередині процесу з високою точністю. Воно може трасувати внутрішні виклики функцій, захоплювати специфічний для застосунку контекст та інструментувати сторонні залежності Go.

## Компроміси {#trade-offs}

| Характеристика               | OBI (eBPF)                                                                                                                     | otelc (Compile-Time)                                                                                                           |
| :--------------------------- | :----------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------- |
| **Модель розгортання**       | Розгортається окремо (наприклад, Kubernetes DaemonSet, sidecar або агент на хості). Жодних змін у конвеєрі збірки застосунку.  | Вбудовується в бінарний файл застосунку під час `go build`. Потребує обгортання вашої команди збірки.                          |
| **Вимоги під час виконання** | Потребує певних версій ядра Linux, BTF та підвищених привілеїв (root/можливості).                                              | Не потребує спеціальних привілеїв під час виконання, функцій ядра або вимог до ОС.                                             |
| **Точність і глибина**       | Відмінно підходить для мережевих меж і взаємодій протоколів. Не може легко бачити внутрішні виклики функцій або власну логіку. | Глибока видимість усередині процесу. Може інструментувати внутрішні функції, власну логіку та шляхи виконання коду.            |
| **Сторонні бібліотеки**      | Бачить мережеві виклики та запити до баз даних, зроблені залежностями.                                                         | Може інструментувати внутрішнє виконання коду залежностей модулів Go.                                                          |
| **Життєвий цикл**            | Можна приєднувати, відʼєднувати, оновлювати або відкочувати динамічно без перезапуску застосунку.                              | Потребує повторної збірки, повторного розгортання та перезапуску застосунку, щоб змінити версії або видалити інструментування. |

## Коли що використовувати {#when-to-use-which}

### Оберіть OBI, якщо: {#choose-obi-if}

- **Ви надаєте перевагу простоті розгортання та негайному зворотному звʼязку:** Розгортання агента OBI дає змогу збирати телеметрію без зміни життєвого циклу розробки програмного забезпечення (SDLC) або процесів збірки.
- **У вас парк застосунків різними мовами:** Ви хочете єдиний уніфікований інструмент автоматичного інструментування, який працює з Go, Java, Python, .NET та іншими мовами.
- **У вас немає доступу до конвеєра збірки:** Ви не контролюєте процес збірки, використовуєте попередньо скомпільовані бінарні файли постачальника або не маєте доступу до вихідного коду.
- **Для вас важлива спостережуваність меж:** Ваша основна мета — відстеження взаємодії між сервісами, метрик RED та викликів до баз даних по всій вашій інфраструктурі.
- **Ваш застосунок працює під Linux:** Ви використовуєте середовище Linux (усередині або поза Kubernetes) і можете розгорнути агента із необхідними привілеями для спостереження за вашими процесами. OBI надає селектори для інструментування за назвою виконуваного файлу, відкритими портами та PID процесу, а також мітки Container, Pod, Deployment, Namespace та метаданих у контейнеризованих сценаріях (Docker/Kubernetes), що робить його гнучким для різних сценаріїв розгортання.

### Оберіть otelc, якщо: {#choose-otelc-if}

- **Ви контролюєте конвеєр збірки Go:** Ви маєте повний контроль над тим, як компілюються та розгортаються ваші сервіси Go.
- **Вам потрібні гарантії інструментування:** Ви можете писати тести під час фази збірки, щоб переконатися, що зібрана телеметрія точна до розгортання.
- **Вам потрібна максимальна точність відрізків:** Вам потрібне глибоке трасування всередині процесу бізнес-логіки та внутрішніх станів застосунку.
- **Ви хочете трасувати внутрішню роботу сторонніх компонентів:** Вам потрібна видимість виконання сторонніх модулів Go, які ви імпортуєте, але не контролюєте.
- **Ваше середовище виконання обмежене:** Ви працюєте в середовищах, які обмежують привілеї root, можливості eBPF або певні версії ядра (наприклад, деякі безсерверні середовища або сильно захищені контейнерні середовища).
- **Вам потрібне рішення, незалежне від платформи:** Ваш застосунок має працювати на Windows, Linux або macOS, чи на спеціалізованих архітектурах, які вже підтримує середовище виконання Go.

### Спільне використання {#using-them-together}

Оскільки ці інструменти працюють на різних рівнях стека, вони є взаємодоповнювальними і можуть використовуватися разом в одному середовищі:

- Використовуйте **otelc**, щоб створювати глибокі, високоточні трейси для вашої бізнес-логіки Go, внутрішніх викликів бібліотек та власних відрізків.
- Використовуйте **OBI**, щоб забезпечити мережеву спостережуваність на рівні інфраструктури, TCP-метрики на рівні ядра та покриття для будь-яких компонентів, не повʼязаних з Go, або бічних контейнерів, що працюють у вашому середовищі.

Обидві спеціальні групи з інтересів (SIG) планують у майбутньому покращити сумісність між цими двома інструментами.
