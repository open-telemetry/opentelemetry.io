На сайті посилання перевіряються за допомогою **[Lychee][]** із збереженим у системі контролю версій [кешем результатів зовнішніх посилань](#link-cache).

> [!NOTE] Встановлення Lychee локально є необовʼязковим
>
> CI перевіряє посилання в кожному PR, а бот може оновити [кеш посилань][link cache] за вас. Щоб запускати перевірки локально, [встановіть Lychee][lychee-install]; CI встановлює власну фіксовану копію (див. дію `.github/actions/install-lychee`), тому підтримуйте свою локальну версію якомога ближче до неї.

## Перевірка посилань {#check-links}

Щоб перевірити посилання локально, виконайте:

```sh
npm run check:links
```

## Типові команди {#common-commands}

| Команда                           | Обсяг перевірки                                                                       |
| --------------------------------- | ------------------------------------------------------------------------------------- |
| `check:links`                     | Весь сайт                                                                             |
| `check:links:internal`            | Весь сайт, офлайн (без зовнішніх посилань)                                            |
| `check:links:production-internal` | [Виробнича збірка](#production-internal), внутрішні посилання, офлайн                 |
| `fix:link-cache`                  | Псевдонім для `check:links`; використовуйте для оновлення [кешу посилань][link cache] |

Скрипти `check:links` і `check:links:internal` виконуються на збірці `BUILD_KIND`. Докладніше дивіться в [Типи збірки: повна та скорочена][build-kinds].

## Посилання на непубліковані сторінки {#production-internal}

Невиробничі [збірки сайту][build-kinds] містять **чернетки** та сторінки з **датою в майбутньому**, а виробничі збірки їх виключають. Тому посилання на таку сторінку працює в deploy preview і проходить `check:links`, але повертає 404 на виробничому сайті. Скрипт `check:links:production-internal` виявляє це: він виконує офлайн-перевірку на [скороченій][build-kinds] виробничій збірці та повідомляє про кожну сторінку, яка посилається на ціль, яку збірка не створила. Щоб побачити погляд контрибʼютора на невдачу, дивіться [`CHECK LINKS (production, internal)`][pr-check-production-internal].

Виробнича перевірка доповнює `check:links`. Посилання зі сторінок, які виключає [налаштування](#configuration), зокрема локалізовані сторінки з відмінностями, не перевіряються в обох. Зовнішні посилання та [кеш посилань](#link-cache), який записує їхні результати, належать до `check:links`: офлайн-запуск нічого не завантажує, тому не має результатів для запису.

## Конфігурація {#configuration}

Lychee виконується на зібраному сайті (`public/`) з використанням згенерованого (та проігнорованого в git) файлу `lychee.toml`. Скрипт `generate:config:links` створює його з [`lychee.base.toml`][] плюс блоку `exclude_path`, обчисленого з front matter сторінок, який має два джерела:

- **`link_check_exclude_path`** — список регулярних виразів шляхів відносно сайту для сторінок, які перевірка посилань має пропустити, наприклад, пагінацію блогу та старі дописи; див. [`content/en/blog/_index.md`][blog-index]. Почніть шаблон з `^(../)?`, щоб він охоплював усі локалі: необовʼязковий `../` відповідає дволітерному сегменту шляху локалі, такому як `ja/`.
- **`drifted_from_default`** — [локалізовані сторінки з відмінностями][drifted], статус `true` (змінено відповідник EN) або `file not found` (відповідник EN видалено). Посилання _з_ такої сторінки не перевіряються, оскільки вони можуть бути застарілими, але сторінка залишається дійсним цільовим посиланням: вхідні посилання з синхронізованих сторінок, включно з фрагментами, все ще перевіряються.

Збережені статуси відхилення актуальні лише настільки, наскільки свіжа остання нічна синхронізація статусів [Housekeeping][] (як обʼєднана, тому вік може перевищувати день), тому генератор також пропускає сторінки з **очікуваним відхиленням**: локалізовані копії англійських сторінок, змінених (або видалених) після **базового рівня статусу відхилення** — коміту головної гілки, записаного в `data/l10n-drift.yaml` при загальній синхронізації статусів (`npm run fix:i18n`). Копія, яка сама змінилася після базового рівня, залишається перевіреною: хтось працює над нею. Генерація конфігурації завершується помилкою, якщо базовий рівень відсутній або не може бути знайдено; у CI завдання перевірки посилань спочатку поглиблюють свої поверхневі клони до базового коміту; локально отримайте відсутню історію (`git fetch upstream main`) або перевизначте базовий рівень: `DRIFT_BASELINE=HEAD npm run check:links` очищає накладання (пропуски за збереженим статусом все ще діють).

Локальна загальна синхронізація статусів (`npm run fix:i18n`) може перезаписати `data/l10n-drift.yaml`; залиште цей перезапис незафіксованим — локально записаного коміту може не існувати у вихідному репозиторії.

## Link cache <a id="refcache"></a>

Результати перевірки зовнішніх посилань кешуються у **`link-cache.jsonc`**, зафіксований кеш, який підтримує пакунок [link-cache][]; власний файл кешу Lychee, `.lycheecache`, виводиться з нього за кожним запуском і ігнорується git. Щодо формату файлу, включаючи те, як вручну додати запис, див. [Власний кеш][cache-format]; щодо того, які URL перевірка завантажує, а які віддає з кешу, див. [Операційна модель][Operating model]. Ручні правки — лише для навмисного засіювання; для URL, який просто блокує перевірку посилань, додайте `?link-check=no` до нього (див. [Обробка дійсних зовнішніх посилань][Handling valid external links]).

Кеш регулярно оновлюється кількома [запланованими робочими процесами](#workflows), а також PR із змінами вмісту, тому одноразові оновлення можуть конфліктувати під час 3-way merge Git, включаючи різні URL: обидві сторони вставляють у той самий відсортований проміжок, або одна сторона обрізає запис, який інша оновила або вставила поруч (такий фрагмент може тоді розділити запис). Коли зміни кешу гілки — це рутинні результати перевірки, бери файл `main` повністю і повторно запусти перевірку, яка повторно додасть все, що потрібно гілці; інакше слідуй правилам конфліктів у [Власний кеш][cache-format], потім повторно запусти перевірку для нормалізації файлу.

Якщо ви додаєте або змінюєте зовнішні посилання, запустіть `npm run check:links` **перед надсиланням PR** — збірка сайту займає більшу частину часу — та зафіксуйте оновлений `link-cache.jsonc` разом із змінами вмісту. Інакше перевірка `CACHE updates committed?` зазнає невдачі; для відновлення дивіться [`CACHE updates committed?`][pr-checks].

## Робочі процеси оновлення кешу та обслуговування {#workflows}

Наступні робочі процеси виконуються щодня та запускають команду перевірки посилань:

| Робочий процес                                                | Команда перевірки посилань                       |
| ------------------------------------------------------------- | ------------------------------------------------ |
| Оновлення refcache                                            | `log:check:links` (повна збірка, після очищення) |
| [Housekeeping][] (`fix-and-test:all`)                         | `fix:link-cache` (повна збірка)                  |
| [Автооновлення версій реєстру][Auto-update registry versions] | `fix:link-cache`                                 |

Оновлення refcache спочатку очищає найстаріші записи кешу (кількість є вхідним параметром робочого процесу) і повторно запускає перевірку посилань, яка оновлює записи кешу для очищених URL, що все ще використовуються на сайті.

### Повторна перевірка невдалих посилань {#double-check}

Деякі сайти показують браузерам дійсні сторінки, але відмовляють простим HTTP-клієнтам, як-от Lychee (захист від ботів, безумовні відповіді 404 від crates.io, перенаправлення на сторінку входу npmjs.com). Оскільки [кешована невдача повторно завантажується при кожному запуску][Operating model], посилання на такі сайти інакше провалювали б перевірку щоразу.

Інструмент **double-check** повторно перевіряє зафіксовані Lychee невдачі через пробу на рівні вебоглядача. URL, які проба успішно розвʼязує, записуються у `link-cache.jsonc` з синтетичним статусом `206` («OK by analysis»); URL, які вона не може розвʼязати, зберігають невдачу, записану перевіркою, для опрацювання в PR оновлення. Робочий процес Refcache refresh запускає його після перевірки посилань; щоб запустити його локально на основі збереженого журналу:

```sh
npm run log:check:links
npm run fix:link-cache:double-check
```

Спочатку параметрів виконайте `npm run fix:link-cache:double-check -- --help`. Щодо поведінки зонда та налаштування дивіться [double-check README][].

## У CI {#in-ci}

Робочий процес [`check-links.yml`][ci] збирає сайт (скорочено) у своєму завданні `BUILD` та передає цей артефакт завданню `CHECK LINKS`, тому локальні запуски та CI перевіряють ту саму збірку. Це завдання завершується помилкою, якщо будь-яка перевірка посилань не вдається, і передає оновлений кеш завданню `CACHE updates committed?`, яке завершується помилкою, якщо після запуску зафіксований `link-cache.jsonc` залишається застарілим.

Завдання `CHECK LINKS (production, internal)` виконується поряд із `BUILD`, зі своєю власною збіркою: воно запускає [`check:links:production-internal`](#production-internal).
