npm-залежності закріплені зафіксованим `package-lock.json`, а встановлення виконують лише перевірені скрипти життєвого циклу. Щодо моделі загроз та обґрунтування цих заходів див. [Безпека ланцюга постачання][Supply-chain security].

## Контракти встановлення {#install-contracts}

CI, devcontainer та Netlify встановлюють із точним блокуванням версій та без скриптів, а потім явно повторно вмикають єдиний перевірений хук: повторну збірку `hugo-extended`, яка завантажує зафіксований бінарний файл Hugo. Збірка виконується через `scripts/rebuild-hugo-extended.mjs`, який повторює завантаження з обмеженим backoff і відмовляється виконуватися, якщо встановлено будь-який `HUGO_*` installer override. Встановлення зберігають опціональні залежності: npm доставляє бінарні файли для потрібної платформи (наприклад, Dart Sass компілятор у `sass-embedded`) як опціональні залежності, обрані за `os`/`cpu`, тому їх вилучення ламає збірку. За середовищами:

- **CI**: `npm run ci:min`; завдання, які збирають сайт, після цього виконують `npm run ci:prepare`.
- **Devcontainer**: `npm run install:safe`, той самий контракт.
- **Netlify**: `npm run install:safe`, який виконує [команду збірки][Netlify] після [inert auto-install](#inert-netlify-auto-install), між перевірками чистоти робочого дерева:
  - Відхилення блокування або будь-які інші зміни, видимі в Git, призводять до збою збірки.
  - Для збоїв на шляхах, яких встановлення ніколи не торкалося, див. [Застарілий кеш збірки Netlify](#netlify-build-cache) нижче.
- **Локально**: `npm run install:safe` або стандартне `npm install`, яке слідує за блокуванням, поки воно узгоджується з `package.json`, і обмежує скрипти життєвого циклу [дозволеним списком](#lifecycle-script-allowlist), а не вимикає їх; див. [локальне налаштування][local setup].

Вкладене налаштування [теми Docsy][Docsy] дотримується того самого контракту: крок `prepare` викликає власне точне, без скриптів, встановлення залежностей теми.

### Застарілий кеш збірки Netlify {#netlify-build-cache}

Netlify зберігає кеш збірки для кожного [контексту розгортання][deploy context]:

- Один для робочої версії
- По одному для кожної **назви головної гілки** у разі попереднього розгортання, що завантажується з кешу робочої версії під час першої збірки за цією назвою. Історія кешу зникає лише в разі явного очищення: видалення гілки не враховується Netlify, тому гілка, відтворена під тією самою назвою (включно з повторно використаними назвами гілок-ботів), знову привʼязується до старого кешу.

Кожен кеш [містить клон репозиторію][includes a clone of the repository], а перехід на коміт, який прибирає git-субмодуль, залишає робоче дерево субмодуля на місці, тож видалений субмодуль може через кеш повернутися у наступні збірки як залишок, який git не відстежує, і призвести до збою перевірок чистоти робочого дерева: журнал розгортання показує шлях у статусному рядку з префіксом `??`.

Видаліть відповідний [кеш збірки][build cache], а не додавайте шлях до `.gitignore`:

- **Робоча версія**:
  - Видаліть кеш і розгорніть сайт: **Deploys** > **Trigger deploy**.
- **Deploy Previews**: кожна зібрана гілка має власну копію кешу, на яку пізніше очищення кешу робочої версії не впливає.
  - Видаліть його зі сторінки останнього розгортання PR: **Retry** > **Clear cache and retry with latest branch commit**. Масового очищення по всім гілках немає.

> [!IMPORTANT]
>
> Після видалення git-субмодуля видаліть кеш збірки робочої версії як частину видалення, до того як залишки поширюються у кеш-копіях гілок. Також видаліть ланцюжок будь-якого переробленого імені бот-гілки; очищення робочої версії ніколи не досягає його.

## Оновлення залежностей {#updating}

Планові підвищення версій надходять як PR від [Renovate][], обмежені [періодом охолодження](#release-cooldown), а виправлення відомих вразливостей надходять за сповіщеннями ([Оновлення безпеки](#security-updates)). Решта випадків робиться вручну; у кожному з них зафіксуйте перегенероване блокування разом із будь-якою зміною `package.json`.

### Зміни маніфесту {#manifest-changes}

Чи ви редагували `package.json` вручну, чи підвищили кожну версію за допомогою `npm run update:packages` (до [періоду охолодження](#release-cooldown) застосовуються версії, що пропонуються), узгодьте блокування із зміненим маніфестом:

```sh
npm install --package-lock-only --ignore-scripts
```

На відміну від `npm update` (нижче), ця команда переписує лише записи блокування, які зачіпає ваша правка маніфесту. Це може бути більше пакунків, ніж ті, що ви редагували: коли підвищений пакунок замінюється, його власні транзитивні залежності (ті, від яких не залежить жоден інший пакунок) можуть бути перевизначені до найновіших версій, допущених їхніми діапазонами та періодом охолодження, тому перегляньте весь дельта блокування.

Конфлікт злиття у файлі блокування вирішується тим самим рецептом: залиште версію з `main` і повторно виконайте команду.

### Пакунки зі скриптами {#script-bearing-packages}

Коли додаєте або оновлюєте пакунок, який має чи потребує запис `allowScripts`, учасник, що вносить зміну:

1. Переглядає скрипти життєвого циклу нової версії.
2. Записує результат, зафіксований разом зі зміною залежності та перевірений під час рецензування PR: потрібний скрипт — як схвалення з точною версією, непотрібний — як заборона на рівні назви (`false`, яка не потребує оновлення при наступних підвищеннях версій).
3. Для нового схвалення також додає пакунок до винятку автоматичного злиття Renovate у [`.github/renovate.jsonc`][]: кожне підвищення схваленого пакунка потребує наведених вище кроків, тож його PR з оновленням мають чекати на учасника.

### Hugo {#hugo}

Два налаштування задають версію Hugo:

- `hugo-extended` у [`package.json`][], точне закріплення: бінарний файл, який використовує кожна збірка, і єдина версія, за якою сайт пройшов перевірку.
- `module.hugoVersion.min` у [`module-template.yaml`][], мінімальна версія: нижче неї Hugo попереджає, а [перевірка журналу збірки][build-log check] перетворює попередження на збої CI.

Мінімальна версія підвищується, коли сайт починає залежати від зміни в Hugo. Наприклад, монтування `files` припускає виправлений механізм пошукових шаблонів (glob) Hugo 0.166.0 (`**/` більше не відповідає нулю тек).

Щоб підвищити версію Hugo:

1. Ознайомтеся з [посібниками з оновлення Docsy][Docsy upgrade guides] для діапазону Hugo.
2. Встановіть версію `hugo-extended` у `package.json` та [узгодьте блокування](#manifest-changes). (`npm run update:hugo` встановлює останню версію замість цього, зі скриптами увімкненими; `strict-allow-scripts` зазнає невдачі, якщо схвалення ще не називає ту версію.)
3. Оновіть [схвалення `allowScripts`](#script-bearing-packages), потім виконайте `npm run install:safe`, щоб завантажити закріплений бінарний файл через переглянутий хук.
4. Підвищте `hugoVersion.min`, якщо сайт тепер залежить від зміни в цьому діапазоні.

### Транзитивне оновлення {#transitive-refresh}

Жоден розклад не перевизначає блокування в цілому ([визначення версій навмисне][deliberate]). Щоб оновити транзитивні залежності, виконайте наступне за потреби в корені репозиторію (блокування також покриває робочий простір `scripts/generate-community-data`):

```sh
npm update --package-lock-only --ignore-scripts
```

Щоб оновити лише деякі пакунки, вкажіть їх:

```sh
npm update --package-lock-only --ignore-scripts PACKAGE_NAME
```

Замініть _`PACKAGE_NAME`_ на пакунок (або пакунки) для оновлення.

Якщо так чи інакше, перегляньте все оновлене блокування: npm також рухає те, що вимагають вибрані версії, і оскільки він поважає діапазони, оголошені в маніфестах, батьківський пакунок, який розширює діапазон, може потягнути новий транзитивний major.

[Період охолодження](#release-cooldown) застосовується, з гострим краєм: залежність, чиї єдині задовільні версії молодші за період охолодження (точне закріплення — поширений випадок), звалює всю резолюцію (`ETARGET`), доки якась версія не постаріє. Коли молодий випуск — той, який ви переглянули та за який ручаєтесь, звільніть саме цю назву; охолодження залишається увімкненим для решти дерева:

```sh
npm_config_min_release_age_exclude=PACKAGE_NAME \
  npm update --package-lock-only --ignore-scripts
```

Зберігайте виняток лише для конкретного виклику; постійний запис у [`.npmrc`][] назавжди скасував би охолодження для цієї назви.

### Неочікувані зміни блокування {#lock-drift}

Якщо блокування змінилося, але ви не змінювали залежності (перевірка `postinstall` попереджає, коли встановлення робить це), це ознака відхилення: відновіть блокування та дослідіть причину, а не фіксуйте перезапис.

### Оновлення безпеки {#security-updates}

Виправлення відомих вразливостей не чекають на щотижневі PR з оновленнями; вони надходять за сповіщеннями:

- **GitHub [Dependabot security updates][]**: налаштування на рівні репозиторію (без `dependabot.yml`), здатне виправляти як прямі, так і транзитивні залежності; для npm це може означати перезапис записів батьківських маніфестів, а не лише блокування.
- **PR [Renovate][] про вразливості**: відкриваються негайно, для прямих залежностей.

Перетин навмисний; випадковий дублікат PR приймається. Оскільки заплановані перевизначення блокування [вимкнено за дизайном][deliberate], ці шляхи сповіщень є єдиним автоматичним способом виправлення транзитивних залежностей, тож налаштування на рівні репозиторію залишається увімкненим. Коли жоден з них не відкриває PR, супровідник оновлює пакунок [за назвою](#transitive-refresh): ручний шлях. Два шляхи по-різному ставляться до [періоду охолодження](#release-cooldown):

- Безпекові оновлення Dependabot навмисно обходять будь-який поріг віку випуску (включно з `.npmrc`): версія з виправленням, молодша за період охолодження, може зійтися, і її перевірка — обовʼязок супровідника, який рецензує.
- PR Renovate підпорядковується порогу `.npmrc`, коли він перегенеровує блокування, тож виправлення, молодше за період охолодження, приходить як невдале оновлення артефакту; раннє його прийняття потребує [закріпленого винятку](#transitive-refresh), виконаного супровідником.

## Заходи безпеки ланцюга постачання {#controls}

### Аудит ланцюга постачання {#audit}

Тест аудиту ланцюга постачання, [`scripts/supply-chain-audit.test.mjs`][], перевіряє заходи нижче лише з зафіксованих файлів при кожному запуску `test:local-tools`, щоб регресія заходу виявлялася тестом, а не чекала на інцидент. Щодо принципів перевірки, що лежать в основі самого аудиту, див. його [сторінку дизайну](../../design/supply-chain-audit/).

Коли аудит не проходить у вашому PR, повідомлення стверджування вказує очікувану умову; поширені випадки:

- **Ви підвищили залежність, що має запис `allowScripts`**: дивіться в [пакунках зі скриптами](#script-bearing-packages); повідомлення про помилку називає версію, до якої запис має бути перенесено.
- **Ви змінили скрипт шляху встановлення, `.npmrc` або `netlify.toml`**: це помилка і є метою аудиту. Аудит закріплює поверхню встановлення так, що кожна зміна її проходить свідомий перегляд. Оновіть відповідне твердження разом із вашою зміною, і поясніть чому в PR.

Ніколи не послаблюйте твердження просто щоб отримати зелений статус: кожне з них забезпечує захід на цій сторінці, тож спочатку визначте, який захід послаблює ваша зміна.

Поза межами аудиту: <a id="audit-out-of-scope"></a>

- GitHub workflow файли: тригери та привілеї токенів переглядаються для кожного робочого процесу, в [CI workflows][ci-security]
- [Renovate][] конфігурація ([`.github/renovate.jsonc`][]): переглядається як код, не закріплена аудитом
- Власне встановлення залежностей теми [Docsy][] (відстежується upstream)
- npm скрипти збірки після межі встановлення: вони виконують власний код сайту повністю і змінюються в ході нормальної розробки

### Період охолодження випусків {#release-cooldown}

Визначення версій ігнорує випуски, молодші за налаштований мінімальний вік.

- **Вимога**: `min-release-age` у [`.npmrc`][]. Субпроєкт `scripts/generate-community-data` є npm-простором, а не окремий дом блокування, тож кореневі `.npmrc` та блокування керують і його визначенням версій.
- **Сфера дії**:
  - Зачіпаються лише операції визначення версій; точні встановлення з блокуванням (`npm ci`) не визначають версії.
  - npm надає перевагу конфігурації проєкту над конфігурацією користувача, тож суворіший період охолодження у вашому власному `.npmrc` тут перевизначається значенням проєкту; щоб зберегти своє для одного виклику, встановіть змінну середовища `npm_config_min_release_age`, яка має вищий пріоритет за обидва.
- **[Renovate][]**: застосовує власний період охолодження до PR з оновленнями, які він відкриває, заданий `minimumReleaseAge` у [`.github/renovate.jsonc`][]; довший для оновлень, які зливаються без рецензування людиною. Триденне охолодження npm із пресета (`security:minimumReleaseAgeNpm`) виключено, щоб воно не могло перевизначити ці віки, включно з його винятками за віком; увага: перейменування цього пресета в upstream мовчки знову допустило б його. Типи оновлень, які Renovate не може датувати (наприклад, `pin`, `replacement`, `rollback`), випадають з-під його охолодження: їхні PR відкриваються зазвичай, у крайньому випадку показуючи постійно очікуваний статус стабільності (не обовʼязкову перевірку), тож звичайне рецензування і є барʼєром.

### Дозволений список скриптів життєвого циклу {#lifecycle-script-allowlist}

Встановлення виконує скрипти життєвого циклу пакунка лише тоді, коли його точна назва та версія внесені до списку дозволів `allowScripts`:

- **Вимога**: мапа `allowScripts` у [`package.json`][], яка стає стандартно закритою через `strict-allow-scripts` у [`.npmrc`][].
- **Де це спрацьовує**: лише на встановленнях зі скриптами, що тут означає крок повторної збірки `hugo-extended` [контрактів встановлення](#install-contracts), де npm перевіряє все встановлене дерево, і локальний `npm install` без `--ignore-scripts`.
- **Заборони**:
  - Запис зі значенням `false` фіксує переглянуту заборону: пакунок встановлюється, його скрипт пропускається.
  - Заборони нічого не надають, тож вони покривають пакунок за назвою, на всіх версіях.
- **Локальне маскування**: `ignore-scripts=true` у вашому користувацькому `.npmrc` робить звичайний `npm install` без скриптів, тому цей шлях обходить дозволений список; крок повторної збірки все ще його оцінює, тому `npm run install:safe` перевіряє позицію репозиторію незалежно від вашої користувацької конфігурації.

### Мінімальна версія npm {#npm-version-floor}

Встановлення завершується збоєм, коли активний npm старший за мінімальну версію engines: найстарішу версію, яка підтримує наведені вище заходи.

- **Забезпечення**:
  - `engines` у [`package.json`][] задає мінімальну версію. Нижче неї npm не має частини або всіх засобів забезпечення дозволеного списку, або налаштування `min-release-age-exclude`, на якому покладається [виняток транзитивного оновлення](#transitive-refresh); коментар біля `engines` називає випуски. Версії без підтримки `allowScripts` ігнорують це поле мовчазно, тому встановлення зі скриптами запускає кожен скрипт встановлення.
  - `engine-strict` у [`.npmrc`][] перетворює попередження npm `EBADENGINE` на відмову.
- **Політика мінімальної версії**:
  - Мінімальна версія зростає, коли npm виправляє прогалини у забезпеченні цих заходів.
  - Закріплений `.nvmrc` фіксує випуск Node.js, чий вбудований npm задовольняє мінімальну версію, тож CI, Netlify і локальні налаштування під керуванням `nvm` проходять перевірку за побудовою; [Renovate][] оновлює це закріплення. (Плаваючий `.nvmrc`, як-от `lts/*`, не може цього гарантувати: виконавці CI визначають його з можливо застарілих кешів.)
- **Netlify**:
  - Стандартний npm, вбудований у Node від Netlify, може бути старшим за мінімальну версію; [`NPM_VERSION`][netlify-deps] у [`netlify.toml`][] закріплює версію, яка її задовольняє.
  - Оновлюйте закріплення щонайменше тоді, коли зростає мінімальна версія.

### Автоматичне встановлення Inert Netlify {#inert-netlify-auto-install}

Автоматичне [встановлення][netlify-deps] Netlify на початку збірки нейтралізується [`NPM_FLAGS`][netlify-deps] у [`netlify.toml`][]:

- `--dry-run`: npm вирішує та логує, що змінило б встановлення, але нічого не записує.
- `--ignore-scripts`: скрипти життєвого циклу залишаються вимкненими за явною вказівкою, а не як побічний ефект сухого запуску.

**Сфера дії**: `NPM_FLAGS` — це налаштування збірки Netlify, а не конфігурація npm; він застосовується лише до автоматичного встановлення, ніколи до запусків npm у команді збірки.

**Захист у глибину**: [справжнє встановлення][install contracts] — це `npm ci`, яке замінює `node_modules` повністю, тож залишки автоматичного встановлення чи кешу збірки там не переживають збірку, навіть якщо `node_modules` невидиме для перевірок чистоти робочого дерева (вони бачать лише зміни, видимі в Git).

### Жодного голого npx {#no-bare-npx}

Обвʼязка репозиторію (скрипти пакунка, CI, допоміжні скрипти, документація для учасників) ніколи не викликає бінарний файл як `npx BIN`: на застарілому чи відсутньому `node_modules` `npx` звертається до публічного реєстру та виконує будь-який пакунок, якому належить ця назва. Його запит на встановлення не є захистом: він пропускається в неінтерактивних контекстах і провокує бездумне «так» в інших. Локалізовані копії документації для учасників наздоганяють це правило через [відстеження відхилень][drift tracking].

- **Натомість**:
  - Скрипти пакунка викликають бінарні файли, надані залежностями, безпосередньо; npm додає `node_modules/.bin` до їхнього `PATH`, а відсутній бінарний файл завершується гучним збоєм без жодного звернення до реєстру.
  - Контексти без запису в `PATH` (документація, окремі скрипти) використовують `npm exec --no -- BIN`, який ніколи нічого не встановлює.
- **Забезпечення**: дисципліна рецензування; автоматичної перевірки немає.
